How a wall joins today A kiosk Chrome with a persistent profile logs in and opens //chat//?autoJoin=1&mic=…&camera=…&telepresence=1 (PR-029). The telepresence=1 flag only turns on Presentation Mode in the frontend. The backend row it creates is the same as any other user's. Calls run on LiveKit with one room per Call, created 1:1 by liveKitService.ts. There is no multi-room or room-bridging code. What exists to build on, and what does not Missing No mid-call idle state. Every "idle" in roomMachine.ts and callMachine.ts is a pre-join lifecycle state. Missing The "+1 call waiting" banner in IncomingCallModal ends the current call before joining the new one. That forced end is what this project replaces. Missing No way for a person to control a wall. The wall is a kiosk browser with no input device, so nobody can press a button on it. Usable Wall.wallType already has a SWITCHABLE value next to PRIMARY. It is declared and never read, and it is confirmed to exist for this feature. The scenario Wall A is talking to Wall B. Rules the flow follows 1 Switching is always one confirmation. The confirm text names which walls will be parked. 2 The picker lists ongoing calls, parked walls and free walls. Each row shows the wall label and who it is with. 3 Wall A keeps showing its current partner until the new connection is confirmed. If the switch fails, A is still with B. 4 Parked walls always tell the room what happened and who can bring them back. A wall never just goes black. 5 Walls that are not marked SWITCHABLE do not appear in the picker and cannot be parked. Rules for a 140-inch screen People stand two to four metres from these screens, and the feed is life-size. That changes what the wall UI may do. Parked walls Parked is a real connection that is not part of any call. It is the opposite of hanging up. Today the data model only knows "in call" and "left" (CallParticipant.leftAt). Parked is a third state between them. Timeout A parked wall that nobody reconnects ends for real and returns to its home screen. Start with 10 minutes, configurable. That number is a placeholder until whoever owns LiveKit capacity gives a real one. Needs a decision: what "instant" means in LiveKit. A LiveKit participant belongs to one room and tracks cannot move between rooms, so a handshake-free reconnect is not possible. The proposed design keeps each parked wall connected to a per-workspace idle room with a token for the call room already minted. Reconnecting connects to the call room first and leaves the idle room second. That should feel instant, usually well under a second. Please confirm that is acceptable, or measure it before Phase 1. Who is allowed to switch A Wall Controller is paired to exactly one wall. Its token acts as that wall's user, so the backend sees "Wall A asks to switch" and not "a phone asks". Pairing is a one-time step per wall. Which walls must be switchable The switch moves up to four walls: A, B (parked), C (parked) and D (target). All of them must be SWITCHABLE. If any is PRIMARY, the switch is refused with a clear reason and nothing changes. Free walls only need A and D checked. Data model Call and CallParticipant are untouched. WallSession is the new source of truth for which LiveKit room a wall is actually connected to right now, in a call or parked. IdleSession layers the parked business state (who it's parked from, its timers) on top of a WallSession row instead of tracking its own room SID. Wall lives in another database and is read live, never copied. Both use WHERE status='idle', so exactly one wins. API and events ENDPOINT OR EVENT WHAT IT DOES POST /calls/:callId/switch {targetUserId} Moves the caller's wall to the target wall. The target can be in a call, parked or free. No mode field, because there is only one outcome. GET /idle-sessions Lists parked walls in the caller's workspace, with time parked and the call they came from. POST /idle-sessions/:id/release Sends a parked wall to its home screen early. idle_session.created / .resumed / .expired Pushed on the existing realtime channel to wall kiosks and controllers. No polling. wall_session.heartbeat (realtime, not REST) Kiosk and Controller push this on a short interval to refresh WallSession.lastHeartbeatAt. A session whose heartbeat goes stale is what the reconciler treats as dead. GET /api/walls/by-user/:userId (portal) Read-only. Returns {wallType}. Called synchronously for every wall the switch moves. The atomic claim -- target is in a call: only one switch may take it UPDATE calls SET version = version + 1 WHERE id = $callId AND status = 'active' AND version = $seen; -- target is parked: only one switch may reconnect it UPDATE idle_sessions SET status = 'resumed', resumed_into_call_id = $1 WHERE id = $id AND status = 'idle'; -- 0 rows affected => 409 target_unavailable, controller shows "just taken" The timeout job uses the same predicate with status='expired'.
